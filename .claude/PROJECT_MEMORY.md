`TASK-007` is implemented and verified. `backtrader==1.9.78.123` is the new runtime dependency; no schema/DB changes (no migration 0005 — this task is purely in-memory execution, nothing persisted). Empirically verified Backtrader facts (see `backend/app/infrastructure/engine/backtrader_adapter.py`): submitting a Market order via `self.buy()`/`self.close()` during `next()` (default broker config, no `cheat_on_open`) fills at the **next** bar's open by default — no special broker configuration was needed to get next-bar-open semantics. If the eligible signal occurs on the feed's last bar, the order stays `Submitted` forever (never fills) — this is how `missing_next_bar` is detected (any order still pending in the strategy's `stop()` callback marks the run `failed`). Backtrader's own broker enforces cash margin *at the actual fill price* (next bar's open), which can differ from the signal-bar close used for sizing — a `fraction` close to `1.00` combined with a rising price between signal and fill can cause a legitimate `Margin` order rejection; this is correct/expected behavior (an order can legitimately reject), not a bug, and manifests/tests should choose a `fraction` with headroom if they want a guaranteed fill. The adapter never trusts Backtrader's internal float OHLCV values for persisted output — it converts `Decimal` bars to `float` only for signal-timing indicators/feed, and looks up the exact `Decimal` price from the original bar snapshot (matched by index) for every fill/cash/position event, so no float precision ever leaks into `FillEvent.price` etc. `BacktestRunStatus`'s transition table (`app/domain/backtest_run.py`) was extended to allow `created → failed` directly (previously only `created → running|cancelled`), needed for pre-flight rejections (unsupported multi-instrument, unresolved instrument mapping, empty bar snapshot) that must fail before a run is meaningfully "running". `POST /api/v1/backtest-runs/{run_id}:execute` is a deliberately minimal, non-final endpoint returning only event *counts* and terminal status — no event payloads, no persisted/retrievable artifact (TASK-008 owns that). v1 rejects multi-instrument manifests outright (contract explicitly permits this fallback).

`TASK-008` is implemented and verified. `TASK-012` is implemented and verified. Migration `0006_add_optimizations.sql` adds `optimizations` (one row per optimization: canonical grid/partitions/objective/tie-break, manifest checksum, lifecycle status, selection audit, sealed-until-completion holdout fields) and `optimization_candidates` (one row per canonical `(fast_window, slow_window)` pair, `pending|rejected|completed|failed`). **Real DuckDB bug found and fixed, same class as TASK-008's:** `optimization_candidates.optimization_id` was originally declared with `REFERENCES optimizations (optimization_id)`; since `optimizations.status` is updated repeatedly through the lifecycle and DuckDB implements `UPDATE` as delete+insert, any FK referencing that row makes every subsequent status transition throw `ConstraintException: ... still referenced by a foreign key`. Fixed by dropping that FK (matching the pre-existing, deliberate precedent in migration 0005 where `run_order_events.run_id` also has no FK, for the identical reason) — `optimization_id` remains a plain indexed column, consistency enforced entirely in application code. Domain layer (`app/domain/optimization.py`) is pure/DB-free: `canonicalize_grid` produces a deterministic `(fast_window, slow_window)` lexicographic enumeration independent of input order (dedupes + sorts each axis first); `validate_partitions` enforces `train_end < validation_start <= validation_end < holdout_start <= holdout_end`; `validate_partition_bar_coverage` requires `largest_slow_window + 2` real bars per partition (warm-up + one eligible signal bar + one next-bar-open fill opportunity) — this is the same fill-timing fact TASK-007 established, reapplied here as a pre-execution guard; `select_candidate` ranks only candidates with an *available* objective (an unavailable objective literally cannot appear in the eligible set) via tie-break `(-value, slow_window, fast_window, candidate_id)`. `objective_direction` was deliberately **not** implemented as a caller choice — the contract only specifies "highest objective value wins," and every v1 metric (including `max_drawdown`, which is `<= 0`) is already oriented so higher-is-better, so a fixed always-maximize rule satisfies the contract without inventing an unspecified minimize mode. Orchestration (`execute_optimization_service.py`) reuses TASK-006/007/008's `create_strategy_spec`/`create_run_manifest`/`execute_backtest_run` directly — each candidate materializes one new immutable strategy version (name embeds its fast/slow windows) plus a real train-period run and a real validation-period run through the actual Backtrader adapter and artifact-persistence path; nothing about run/strategy/artifact semantics was reimplemented. A candidate's train or validation run failing (e.g. `missing_next_bar`) is caught and recorded as a `failed` candidate with `objective_reason` set — it does **not** abort the remaining candidates (verified in the Docker smoke test: a 4-candidate grid produced 3 `completed` + 1 legitimately `failed`, and the optimization still reached `completed`). The holdout run executes exactly once, only for the selected candidate, only after selection is recorded — `GET /api/v1/optimizations/{id}` computes `holdout.sealed = (status != completed)` at the API-response layer (not just via a DB flag), so even a mid-lifecycle GET can never leak holdout fields regardless of what's already been written to the row. `objective_metric_key` is restricted to the same 9 keys TASK-008 defined (`ALLOWED_OBJECTIVE_METRICS`); an unsupported key is a `422 unsupported_objective` at creation time, before any candidate runs. New typed setting: `APP_OPTIMIZATION_MAX_CANDIDATE_COUNT` (default 50) bounds the *canonical* grid size (valid + rejected pairs together), checked before any execution — an oversized grid creates no optimization row at all (no partial optimization).

Frontend (`lib/api/optimizations.ts`, `app/optimizations/{page,new/page,[optimization_id]/page}.tsx`): `apiFetch` (TASK-009/010) gained a `json?: unknown` option for plain-JSON POST bodies (`optimizations` creation is JSON, not multipart like TASK-010's dataset import) — sets `Content-Type: application/json` and `JSON.stringify`s the body. The create form's live "candidate count" preview is pure combinatorics (counting `fast < slow` pairs client-side) — explicitly not a financial calculation, and the UI never claims it as anything more than a count. Fast/slow window lists use a comma-separated `text` input validated against `/^[1-9]\d*$/` per value (not `type="number"`), consistent with TASK-011's stance on rejecting decimal/scientific-notation values client-side. The detail page computes `holdout.sealed` purely from the API-provided `holdout.sealed` flag (never re-derived from `status` client-side) and renders a distinct `UnavailableState` instead of the holdout fields until unsealed. Nav (`SiteNav.tsx`) gained an "Optimizations" link between Strategies and System status; `SiteNav.test.tsx`'s link-count assertion was updated from 5 to 6.

**Post-TASK-016 fix (retroactive, affects TASK-009 through TASK-016):** `backend/app/main.py` never registered `CORSMiddleware`, so every browser-side `fetch()` from the frontend to the API was silently blocked by the browser (different port = different origin; confirmed via a manual `OPTIONS` preflight returning `405` with no `Access-Control-Allow-Origin` header) — every frontend page showed a generic "Could not reach the API" error despite the API itself being healthy. This had been present since TASK-009 introduced the browser API client and went undetected through every subsequent frontend task because every Docker smoke test used `curl` (which does not enforce CORS) or checked only the SSR shell — no task's verification exercised a real client-side `fetch()` from an actual browser origin. Fixed by adding `CORSMiddleware` with a wildcard origin (`allow_origins=["*"]`, `allow_credentials=False` — required together per the CORS spec, and appropriate here since this is a local-only, single-user, no-auth tool with no session/cookie auth to protect). Caught only because the user ran the app directly and reported the browser-visible symptom; `tests/test_cors.py` now proves preflight success and header presence going forward. **Lesson for future frontend-touching tasks: a Docker smoke test that only uses `curl` or checks SSR HTML does not prove the browser can actually talk to the API — a real cross-origin check (or manual browser verification) is required to catch this class of bug.**

`TASK-019` is implemented and verified. Per the user's request for "strategies usable by professional traders" (clarified via AskUserQuestion to mean curated indicator kinds with configurable parameters, not free-form code — see ADR-012), three new strategy kinds were added alongside `sma_crossover`: `rsi_threshold` (enter on RSI crossing up through oversold, exit on RSI crossing down through overbought), `macd_crossover` (enter/exit on MACD line vs. signal line crossovers), `bollinger_breakout` (enter on a close above the upper band, exit on a close below the middle band). Each is a fixed, deterministic, long-only, single-signal rule with its own frozen parameter dataclass (`RsiThresholdParameters`/`MacdCrossoverParameters`/`BollingerBreakoutParameters` in `app/domain/strategy_spec.py`), its own `required_warmup_bars()` (replacing the old SMA-only `eligible_after_bars >= slow_window` check), and a `build_parameters(kind, raw)` factory that is now the single dispatch point for both parameter construction and kind validation (used by strategy creation and the DuckDB repository's read path; the optimization framework stays `sma_crossover`-only). Migration `0007_expand_strategy_kinds.sql` widens `strategy_specs.kind`'s CHECK constraint via DuckDB's rename-old/create-new/copy-rows/drop-old pattern (same workaround class as TASK-004/TASK-012's DuckDB `ALTER TABLE` limitations) — no FK referenced the old table, so this was a safe data-preserving recreation. The engine adapter (`backtrader_adapter.py`) was refactored from one monolithic `_SmaCrossoverStrategy` into a shared `_BaseCrossoverStrategy` (all order/fill/audit machinery) plus one thin subclass per kind implementing only its own indicators and `_entry_signal()`/`_exit_signal()`; `BacktraderEngineAdapter.execute` now dispatches by `strategy.kind` via a small lookup table. **Empirically-found Backtrader fact:** a perfectly linear price slope makes an EMA-derived indicator (e.g. MACD) converge to exact equality with its own signal line for many bars, and `bt.indicators.CrossOver`/`CrossUp`/`CrossDown` do not fire on an equal-to-greater-than transition (only strictly-less-than to greater-than) — so the MACD engine smoke test deliberately adds small integer noise (`i % 3`, `i % 2`) to its synthetic price series to avoid this false-negative plateau; this is a test-construction detail, not an engine bug. API request/response `parameters` became `dict[str, Any]` instead of a kind-specific Pydantic model (`CreateStrategyRequest`/`StrategySpecResponse` in `app/api/schemas/strategies.py`) — the domain's `build_parameters` factory is the single source of parameter validation, avoiding duplicate validation logic across two layers; an unknown kind or malformed parameters still returns `422 validation_error` with the same envelope. Frontend: `lib/api/strategies.ts` gained a `STRATEGY_KINDS` config table (per-kind fields, defaults, help text, and a `requiredWarmupBars` formula mirroring the backend's domain logic); `/strategies/new` gained a kind `<select>` that swaps the rendered parameter fields and resets them to that kind's defaults; `/strategies` and the strategy detail page render parameters generically from this config instead of hardcoded SMA fields. A custom/combination strategy kind and the run/optimization/strategy picker-UX simplification are explicitly deferred to TASK-020 and TASK-021.

`TASK-020` is implemented and verified. Adds the fifth strategy kind, `multi_indicator_combo` — the "custom" strategy the user asked for, built as a combination of 2-3 existing base indicator conditions rather than free-form code (ADR-013). Entry requires every condition's entry signal on the same bar (AND); exit fires on any one condition's exit signal (OR) — deliberately conservative (harder to enter, easier to exit). `ComboCondition` (kind + one of the four base parameter dataclasses) and `MultiIndicatorComboParameters` (2-3 distinct-kind conditions, `required_warmup_bars()` = max across conditions) live in `app/domain/strategy_spec.py`; `build_parameters` gained a special branch for the combo's nested `{"conditions": [{"kind", "parameters"}, ...]}` shape (the only kind whose raw payload isn't flat scalars), recursing into itself per condition. Migration `0008_add_multi_indicator_combo_kind.sql` widens `strategy_specs.kind`'s CHECK constraint again via the same rename/recreate/copy/drop pattern as migration 0007. **Engine refactor (`backtrader_adapter.py`):** every base kind's indicator-building logic was extracted into one shared `_build_signal_lines(data, kind, params) -> (entry_line, exit_line)` function (using `CrossUp`/`CrossDown` pairs uniformly, replacing the SMA/MACD kinds' prior single `CrossOver` line — behaviorally identical, verified by all pre-existing single-kind tests passing unmodified), used by both each single-kind strategy class and the new `_MultiIndicatorComboStrategy` — this guarantees a condition inside a combo behaves identically to that same kind standalone, not a re-derived approximation. Frontend: `/strategies/new` gained a distinct combo-building UI — selecting "Custom (combine indicators)" swaps to a repeatable 2-3 condition list, each with its own indicator picker and that indicator's fields (defaults to two distinct kinds; add/remove bounded to 2-3, each addition picks the next unused base kind); the strategy detail page renders combo conditions as labeled rows instead of flat fields. Optimization (grid search) remains `sma_crossover`-only, unchanged from TASK-019.
