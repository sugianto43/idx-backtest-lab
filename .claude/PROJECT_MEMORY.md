`TASK-002` is implemented and verified. Backend package layout is `app/{api,application,domain,infrastructure}` (`application`/`domain` are empty package markers — no use cases needed yet). `GET /health` (dependency-free) and `GET /api/v1/health` (service/version) are live. Typed settings (`app/infrastructure/settings.py`, env prefix `APP_`, pydantic-settings 2.14.2) cover environment/log_level/host/port/version. `CorrelationIdMiddleware` accepts/generates an `X-Correlation-Id`, echoes it in the response header, and threads it into structured logs via a contextvar. A single error envelope (`{"error": {"code","message","details","correlation_id"}}`) covers `not_found` (404, unknown routes), `validation_error` (422, request payload errors), and `internal_error` (500, unhandled exceptions — logged locally, never leaked to the client). It deliberately excludes persistence and market-data work.

`TASK-003` is implemented and verified. `duckdb==1.5.5` is the new runtime dependency. Migration 0001 (`backend/migrations/0001_create_initial_schema.sql`) creates `schema_migrations`, `datasets`, and `backtest_runs` (with a DB-enforced FK from `backtest_runs.dataset_id` to `datasets.dataset_id`, checked constraints for status enums and non-negative `warning_count`). The migration runner (`app/infrastructure/db/migration_runner.py`) discovers `.sql` files by filename convention (`NNNN_name.sql`), requires contiguous versions starting at 1, is idempotent, and fails closed on a checksum mismatch or an unknown-newer database version — it runs once at FastAPI startup (`lifespan`), never per-request. `GET /api/v1/ready` reports `database: "ready"` (200) or `dependency_unavailable` (503) without leaking paths. Repository ports (`DatasetRepository`, `BacktestRunRepository`, both `typing.Protocol`) live in `app/application/ports/`; their DuckDB implementations live in `app/infrastructure/db/`. Domain value objects (`DatasetManifest`, `RunManifest`, `BacktestRunStatus` with an explicit `created→running→completed|failed|cancelled` transition policy) are plain validated dataclasses in `app/domain/`, framework-independent. **Important DuckDB fact:** inserting a timezone-aware `datetime` into a `TIMESTAMP` column silently converts it to the *process's local timezone* before storing it as naive — the repositories always convert to naive UTC before insert and reattach `tzinfo=UTC` on read (`app/infrastructure/db/serialization.py`); never pass a tz-aware datetime to DuckDB directly.

`TASK-004` is implemented and verified. Migration 0002 (`backend/migrations/0002_add_market_data_ingestion.sql`) adds `normalized_bars` (DECIMAL(18,6) OHLC, BIGINT volume, FK+CHECK-constrained), `dataset_imports`, and `dataset_validation_events`, plus `datasets.instrument_mapping_policy` (nullable at the DB level — DuckDB 1.5.5 does not support adding a NOT NULL/CHECK column via `ALTER TABLE`, so the allowed-values/required check is enforced in `DatasetManifest.__post_init__` instead). `POST /api/v1/datasets:import` (multipart) validates the CSV against `docs/CSV_INGESTION_CONTRACT.md` byte-for-byte (exact header, UTF-8 only, positive finite decimals, non-negative integer volume, `low<=open,close<=high`, unique+chronological `(instrument_identifier, timestamp)`, no extra columns) and rejects the *entire* file on the first violation — no partial success. A rejected import still persists an audit record (`dataset_imports` row with `status=rejected` + one `dataset_validation_events` error row) with no dataset/bars created. Accepted imports (`valid`/`warning`) write `datasets` + `normalized_bars` + `dataset_imports` + any warning events atomically in one DuckDB transaction (`DuckDBDatasetImportWriter`). Warnings (not rejections): `adjustment_policy=unknown`, any zero-volume row. Re-importing identical file bytes (same SHA-256 checksum) returns `409 conflict` unless the caller sets `allow_reimport=true`. `GET /api/v1/datasets/{id}` and `GET /api/v1/datasets` expose provenance/status/warnings/pagination; neither ever returns raw bars/files/paths. The CSV parser is behind an application-owned `CsvParser` port (`app/application/ports/csv_parser.py`) so application code never imports the infrastructure parser directly — same inward-dependency pattern as the repository ports. Ambiguity flagged and deliberately not implemented: the contract's "mixed interval" rejection scenario has no concrete meaning under the current CSV header (interval is a single declared upload-metadata value, not a per-row column), so no such check/test exists — revisit if a future contract version adds a per-row interval column.

`TASK-005` is implemented and verified. Migration 0003 (`backend/migrations/0003_add_instruments_and_corporate_actions.sql`) adds `instruments`, `instrument_aliases`, `dataset_instrument_mappings`, and `corporate_actions` (the latter with a self-referential `supersedes_event_id` FK, verified to work in DuckDB 1.5.5). Instrument identity is a stable opaque `instrument_id`; ticker symbols are effective-dated `instrument_aliases` rows, never primary keys. A TASK-004 dataset's raw `source_instrument_identifier` resolves to an instrument only for a declared date range via `dataset_instrument_mappings` — the original `normalized_bars.source_instrument_identifier` is never touched. Overlap detection (aliases: same `symbol`+`exchange_code`; mappings: same `dataset_id`+`source_instrument_identifier`) is done in Python (`app/domain/date_ranges.py::date_ranges_overlap`, treating a `None` `effective_to` as open-ended/unbounded) over candidate rows fetched by the non-overlap-aware indexed columns — DuckDB has no native date-range-exclusion constraint, so this is application-enforced and returns `409 conflict`. Corporate actions are immutable evidence only (`payload` is an arbitrary JSON object stored as text, no adjustment math anywhere); a correction is a brand-new event with `supersedes_event_id` set — the original event row is never mutated or deleted. `exchange_code` is restricted to `IDX` only and `instrument_type` to `equity` only (both via DB `CHECK` and domain validation), matching the contract's stated initial scope.

`TASK-006` is implemented and verified. Migration 0004 (`backend/migrations/0004_add_strategy_specs_and_run_manifests.sql`) adds `strategy_specs` (PK `(strategy_id, version)`, `kind` CHECK `'sma_crossover'` only) and extends `backtest_runs` (from TASK-003) with nullable `schema_version`, `manifest_checksum`, `strategy_id`, `strategy_version` columns — the pre-existing `configuration_json` column is reused to store the canonical run-manifest JSON (exactly as TASK-003 anticipated: "exact schema is owned by TASK-006"), and `strategy_spec_version`/`engine_version` are populated with `"{strategy_id}@{version}"` and the manifest's `engine_ref.adapter_version` respectively. Canonical serialization: `app/domain/checksum.py` — `json.dumps(sort_keys=True, separators=(",", ":"))`, checksum is `"sha256:" + sha256(...).hexdigest()`; every nested manifest/spec value object exposes `to_canonical_dict()`. Decimals are preserved as exact strings via `format(value, "f")`, never round-tripped through float. Every POST always creates a brand-new `strategy_id`/`run_id` — there is no update/idempotency-key policy (documented choice, matches the contract's "absent such a policy, create a distinct run ID" fallback). **Deliberate v1 scope reduction:** most execution-assumption fields required by the contract (commission/tax/slippage=`none`, liquidity/price_limit=`ignore_with_warning`, signal_time=`bar_close`, fill_time=`next_bar_open`, benchmark=`none`, corporate_action_treatment=`dataset_as_declared_no_event_adjustment`) are fixed Python constants materialized into every persisted/checksummed manifest — they are NOT caller-configurable API request fields, since the contract itself defines exactly one legal v1 value for each. Only strategy ref, dataset ref, instrument universe, period, capital, position-sizing fraction, rounding, and metrics settings are caller-supplied. `period.bar_interval` is always derived from the referenced dataset's own `bar_interval` (never a separate caller input), which makes "dataset interval must equal requested interval" true by construction rather than a validated-and-possibly-failing check.

`TASK-007` is implemented and verified. `backtrader==1.9.78.123` is the new runtime dependency; no schema/DB changes (no migration 0005 — this task is purely in-memory execution, nothing persisted). Empirically verified Backtrader facts (see `backend/app/infrastructure/engine/backtrader_adapter.py`): submitting a Market order via `self.buy()`/`self.close()` during `next()` (default broker config, no `cheat_on_open`) fills at the **next** bar's open by default — no special broker configuration was needed to get next-bar-open semantics. If the eligible signal occurs on the feed's last bar, the order stays `Submitted` forever (never fills) — this is how `missing_next_bar` is detected (any order still pending in the strategy's `stop()` callback marks the run `failed`). Backtrader's own broker enforces cash margin *at the actual fill price* (next bar's open), which can differ from the signal-bar close used for sizing — a `fraction` close to `1.00` combined with a rising price between signal and fill can cause a legitimate `Margin` order rejection; this is correct/expected behavior (an order can legitimately reject), not a bug, and manifests/tests should choose a `fraction` with headroom if they want a guaranteed fill. The adapter never trusts Backtrader's internal float OHLCV values for persisted output — it converts `Decimal` bars to `float` only for signal-timing indicators/feed, and looks up the exact `Decimal` price from the original bar snapshot (matched by index) for every fill/cash/position event, so no float precision ever leaks into `FillEvent.price` etc. `BacktestRunStatus`'s transition table (`app/domain/backtest_run.py`) was extended to allow `created → failed` directly (previously only `created → running|cancelled`), needed for pre-flight rejections (unsupported multi-instrument, unresolved instrument mapping, empty bar snapshot) that must fail before a run is meaningfully "running". `POST /api/v1/backtest-runs/{run_id}:execute` is a deliberately minimal, non-final endpoint returning only event *counts* and terminal status — no event payloads, no persisted/retrievable artifact (TASK-008 owns that). v1 rejects multi-instrument manifests outright (contract explicitly permits this fallback).

`TASK-008` is implemented and verified. Migration 0005 (`backend/migrations/0005_add_run_artifacts_and_metrics.sql`) adds `run_artifact_bundles` (one row per terminal run, `UNIQUE run_id`, `CHECK terminal_status IN ('completed','failed')`), `run_order_events`/`run_fill_events`/`run_position_events`/`run_cash_events`/`run_warnings` (append-only, `(bundle_id, sequence)`-indexed), `portfolio_snapshots` (`UNIQUE(bundle_id, sequence)`), `run_metrics` (`UNIQUE(bundle_id, metric_key)`), and `reproducibility_manifests` (`UNIQUE bundle_id`). `execute_backtest_run_service.py` now writes the artifact bundle *after* the run's terminal status transition commits, not before — persisting first caused a DuckDB `ConstraintException` (`still referenced by a foreign key in a different table`) because DuckDB implements `UPDATE` as delete+insert, which transiently violates FK constraints on rows already referenced by a child table; this ordering is required for any future artifact table that FKs to `backtest_runs.run_id`. Domain layer (`app/domain/run_artifact.py`): `build_portfolio_snapshots` values cash+holdings at each declared bar's close only (v1 valuation policy, no forward-fill), always `status=valid` in v1; `compute_fifo_realized_pnl` matches SELL fills against BUY lots oldest-first, one realized-P&L entry per SELL fill, net of that fill's own commission/tax/slippage; `compute_metrics` returns the 8 contract metrics (`initial_equity`, `final_equity`, `total_return`, `annualized_return`, `max_drawdown`, `trade_count`, `win_rate`, `realized_pnl`, `exposure_time_ratio`) each as `available`/`not_available` with a reason — never a fabricated/zero-substituted value. A `FAILED` terminal run's bundle persists only its events/warnings; snapshots and metrics lists are empty (no rows written), per ADR-007's "no fabricated portfolio or metric data" rule. Bundle checksum covers provenance + terminal_status + failure_code + counts (not the full event payload); the separate reproducibility manifest checksum covers the full canonical run manifest (`RunManifestV1.to_canonical_dict()`) plus provenance and counts — exported via `GET /api/v1/backtest-runs/{run_id}/reproducibility-manifest`. Seven new read endpoints under `/api/v1/backtest-runs/{run_id}/{summary,artifacts,events,portfolio-snapshots,metrics,reproducibility-manifest,comparison-compatibility}`; `events` takes a required `type` query param (`order|fill|position|cash|warning`) and paginates like the existing list endpoints. `comparison-compatibility` returns a boolean + human-readable reasons (never a numeric ranking), comparing manifest schema version, capital currency, bar interval, annualization basis, dataset adjustment policy, and artifact schema version between two runs. The pre-existing `POST /api/v1/backtest-runs/{run_id}:execute` response `note` field (added in TASK-007, says artifacts are "introduced in a later task") was deliberately left unchanged — an existing TASK-007 test asserts on that exact wording, and updating it is out of TASK-008's scope.

`TASK-009` is implemented and verified. No new dependencies — the client uses native `fetch`/`AbortController` only. One typed API-transport module (`lib/api/`): `config.ts::resolveApiBaseUrl()` reads `NEXT_PUBLIC_API_BASE_URL`, validates it's a parseable `http(s)` URL, and never falls back to a guessed host — missing/invalid config is a `config_error` `ApiResult`, not a thrown exception. `client.ts::apiFetch<T>()` is the *only* function that calls `fetch` for product/system API access; it normalizes every failure mode to one `ApiError` union (`config_error | network_error | timeout | malformed_response | api_error`), reads `X-Correlation-Id` off the response header, and prefers the backend's own `error.correlation_id` when the body matches the documented envelope. `health.ts` wraps `GET /health` (liveness only, per contract) and `GET /api/v1/ready`. Because Next.js inlines `NEXT_PUBLIC_*` env vars at *build* time, a production build must be rebuilt if the API base URL changes — `next dev` re-reads it per request, so this only matters for `next build`/Docker production images; documented in `frontend/README.md`. Global shell (`app/layout.tsx`): skip link, `<header>`/`SiteNav` (client component, `usePathname` + `aria-current="page"`), single `<main id="main-content">` landmark wrapping route content, `<footer>`/`Disclaimer`. Route pages themselves render no `<main>` of their own (avoids a duplicate main landmark) — `page.test.tsx` was updated to assert this. Five routes: `/` (landing), `/datasets` and `/runs` (placeholder, own by TASK-010), `/strategies` (placeholder, owned by TASK-011), `/system` (client component; calls liveness then readiness in sequence and renders one of five distinct states — loading, API-unavailable [`ErrorState` + `UnavailableState`], database-unavailable [`WarningState`, derived from an `api_error` with `code=dependency_unavailable`], unexpected-error [`ErrorState`], or ready). Reusable status components live in `components/status/`: `LoadingState`/`UnavailableState`/`WarningState` use `role="status"` (polite), `ErrorState` uses `role="alert"` and renders message + optional code + optional correlation ID only — never a raw response body or stack trace. `vitest.config.ts` needed an explicit `resolve.alias` for `@/*` (vite/vitest does not read `tsconfig.json`'s `paths` automatically) — without it, every `@/...` import resolved fine under `tsc`/Next.js but failed at test-run time.

`TASK-010` has been specified but not implemented. Its dashboard UX displays dataset provenance/import state and backend-produced run evidence, including explicit warnings and unavailable metric states. Charting, ranking, and browser-side financial computation remain prohibited.

`TASK-011` has been specified but not implemented. It limits browser authoring to the immutable declarative SMA-crossover strategy v1, with backend-authoritative validation and transparent timing/long-only constraints. It does not evaluate strategies or create runs.

`TASK-012` has been specified but not implemented. ADR-009 limits optimization to deterministic finite SMA grids with chronological train/validation/one-time sealed holdout evaluation. Every candidate and failure is immutable/auditable; the product must label output as research-only.
